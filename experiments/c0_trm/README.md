## 手順（実際に行った順）

1. 仕様 r3・予測・凍結を読み、`shasum -a 256 -c ../freeze-c0-trm.txt` が OK であることを確かめた（実行時の G7 でも照合）。
2. Lean: 仕様 r3 は Lean の statement を定めておらず、今回の許可範囲に `formal/` がないので、新しい statement は書いていない。
   既存の `formal/` を `sh formal/check.sh` で型検査した: exit 0、エラー 0、sorry 0、使っている公理は `propext`・`Classical.choice`・`Quot.sound` だけ（`out/formal-check.out`）。
3. `TrmC0.jl`（Float32 の BLAS 行列積で前向き・逆向き、AdamATan2、Float64 でも動く汎用の型）と `c0_trm.jl` を書き、`/tmp` の使い捨ての台本で部品を試した。試しの途中で分かったこと:
   - Base の `exp` が遅さの大半だった（1 ブロック 27 ms）。Float32 は Cephes の expf の式に替えた（1 要素 1.2 ns、Base は 9.8 ns）。
   - OpenBLAS で `C(512×32) += A·Bᵀ`（gate_up の重み勾配）だけが 37 ms と極端に遅く、転置の形 `(32×512)` なら 1 ms。転置の形で溜めて最後に足す形にした。
   - 8 本並列にすると 1 本あたりが単独の 3 倍ほど遅くなる。チャンクを小さくしても、注意の小さな積を BLAS からループに替えても速くならなかった（どちらも戻した）。
     この機械では同時に別のエージェントのジョブ（`core/check/jl_scenarios.jl` など）が動いていて、負荷平均は 15〜17 だった。
   - そのため、1 回の更新の中の同じ入力の例を 1 列にまとめる形にした（下の「実装の選択」。数式上同じ勾配で、G2(d) で確かめた）。これがないと G-TIME の推計が 3 時間を超えていた。
4. 乾式運転（`/tmp` の写しで種子の集合を縮め、学習 3 歩）で流れを通した。これで次の 4 点を見つけて直した（乾式の出力は使っていない）。
   - **G2(a) の関門の組み立ての誤り**: Julia のクロージャの中の `worst`・`per` が外側の同名の変数と共有され、負の対照の 2 回目の呼び出しが正の結果を上書きしていた。
     モデルの勾配そのものは、別に組んだ試しで数値微分と合っていた（1x1・L=2・H=2・ACT 2 手）。`local` を付けて直した。
   - G3 の予測を 64 列のチャンクで 1,200 回回していて遅かった。1 列の作業域にした（元と改変の入力は同じ位置で計算するので、ビット比較の条件は同じ）。
   - 学習の記録の整形の添字（短い学習でだけ起きる）、g6 モードのトップレベルの for の中の代入（soft scope）。
5. 本実行（`-t 8` → `out/`、10,524 秒）。学習前の関門 510 秒、学習 48 本 8,679 秒、予測 516 単位 1,173 秒。学習後の G1 で obs-full rev の TRM が不合格。
6. G1 の不合格を受けて、保存した重みと G1 の束だけを読む診断 `diag_g1.jl` を走らせた（`out/diag_g1.out`）。関門の判定は変えていない。
7. 別プロセスの再実行（`-t 8` → `out-rerun/`）、`-t 1` での学習 2 本のやり直し（`t1` モード）、G6・G8（`g6` モード）。結果は下の「再実行（G6）と G8」。

### G1 の不合格の診断（`diag_g1.jl` → `out/diag_g1.out`、実行後の診断で関門ではない）

同じ重みの Float64 の前向き（TrmC0 は型に汎用）を基準にした。

- rev の TRM: Float32 と Float64 の z_H の差は H 巡ごとに 5.3e−6 → 2.6e−5 → 7.4e−5 → 9.5e−4 → … → 5.6e−2（9 巡目）と増える。最終 ACT 手の logits の Float64 からのずれは TrmC0 0.12、TrmDet 0.18 で、どちらの Float32 実装も同じ程度にずれる。
  食い違いは問い位置以外に集中していた（最大 0.26 は例 5・位置 30・語 7）。問い位置の語 7・8 の logits の差は 1.1e−2 以下、**問い位置の p の差は TrmC0 対 TrmPort 1.6e−5、対 TrmDet 4.3e−6、TrmPort 対 TrmDet 2.0e−5**。
- stat の TRM: z_H の差は全巡で 1.4e−6 以下で増えない。8 入力の問い位置の p は**すべて 0.99188**（入力に依らない定数）。
- rev の TRM の 8 入力の p は 0.98900〜0.99244 で、入力によってわずかに違う。

## 推論（未検証）

- obs で TRM が RATE の水準にとどまったのは、800 更新・バッチ 64・lr ≤ 1e−3 の AdamATan2（1 歩の大きさは座標ごとに 1.27·lr 以下）では、応答率 0.992 の世界の弱い信号を、深い再帰（最後の巡だけで 14 ブロック）を通して拾えなかったためと見られる。
  根拠は、stat の TRM の p が入力に依らない定数 0.99188 だったこと、obs-full と obs-ay の val・学習の損失がほぼ同じだったこと、同じ入力と同じ更新数の TRM-1x1 は TAB4 に近づいた（0.039 対 0.034）こと。
  exo では TRM も入力を使えている（RATE に +0.40）ので、配線の誤りではないと読む（前向きは G1 の学習前・stat で、逆向きは G2(a) で確かめている）。
  反証条件: 同じ実装で S_train を増やしても（または lr を変えても）obs の TRM の p が入力に依らないままなら、この読みは弱まる（ただしそれは凍結の外の実験で、ユーザーの判断が要る）。
- TRM 対 TRM-1x1 で TRM が負けたことは、「H/L 反復と ACT 多段学習を合わせた構成」がこの学習量では不利に働いたことを示すが、どちらの要素のせいかは分けられない（仕様どおり単独に帰属しない）。
- TAB_R1（直前の 6 受容器と行為の表、130 鍵）が obs の 5 基準の中で群を抜いて良い（0.013 対 TAB4 0.034）。S57 の身体の行為の選び方が受容器（y の閾値）に強く結びついているためと見られ、受容器を読む予測器の基準として TAB_R1 を主対照にした r2 の判断が効いた。
- G1 の不合格は、学習した rev の TRM の再帰が Float32 の丸めを 1 万倍ほど増幅することによると見る（TrmC0・TrmDet の両方が Float64 から同じ程度にずれ、stat の TRM では増えない）。
  評価に使う問い位置の p への影響は 2e−5 以下なので、obs-full rev の比較の結論（差は 1e−3 の桁）は実装の選び方では変わらないと見る。ただし G1 の基準は全位置の logits と z_H の 1e−4 なので、関門としては不合格のまま。
- OOD の「一般化失敗」は、分布内（eval rev）でも TRM が B1 に 2 勝 22 敗で負けているので、周期の変更に固有の失敗とは言えない。P-S64-5 の成立はこの意味で情報が少ない。
- ê・ê_cal が p_cal に負けたこと（O1^cal < 0）は、外れが 1% 前後で、単調な較正 p_cal が強い基準であることと、ê_cal の 200 歩（1 歩 ≤ 1.27e−3）が少ないことの両方と整合する。どちらが主かは分けていない。

## 言えないこと

- この結果は凍結した学習量（S_train 800、4 設定）での TRM の成績で、TRM という構成が obs の予測に向かないことは言えない。
- ê の情報量について、p_cal を超えないことは言えるが、ê が何を表しているかは言えない。
- G1 の不合格を「実装は正しい」と言い換えることはしない。言えるのは、Float64 の基準から TrmC0 と TrmDet が同じ程度にずれ、評価の p への影響が小さいことまで。
- `phenomenal_claim` は `:not_certified` のまま。予測器の成績は経験や主体性についての主張ではない。

## 実装の選択（仕様が値を定めていない所。すべて本実行の前に決め、結果を見て変えていない）

- **ê の損失係数** `CE = 1.0`（仕様は G2(b) の 0 と 10 だけを定める）。stop-gradient なので本体・`lm_head`・`p_a` には効かない（G2(b) でビット一致）。
- **各 ACT 手の損失**: 選んだ行為の問い位置の二語 stablemax の `−log p(Y)`。ê は同じ手の `z_H` と `p` から `e_target = ((p ≥ 0.5) ≠ Y)` を作る。どちらも 3 手（1x1 は 1 手）の平均で 1 回更新。
- **初期化の順**: `embed_tokens` → 層 0（qkv, o, gate_up, down）→ 層 1 → `H_init` → `L_init`。各配列は公式の形の行優先の順に埋める。Box-Muller は一様乱数 2 個から正規 1 個（cos 側）、`|z| > 2` を棄却。
- **q_head**: 学習しない（損失・停止に使わない、§3.1 第 3 項）。束の形式のため公式の初期値（重み 0、バイアス −5）で持つ。
- **RoPE 表**: `TrmPort.RotaryEmbedding(8, 47, 10000)`（Float32、`(47, 8)`）。学習・評価・G1 の束で同じ表。
- **exp**: Float32 の学習と評価では Cephes の expf の式（範囲縮小と 6 次多項式、`[−87, 88]` に切る、相対誤差 ≤ 8e−8）。Float64（G2）では `Base.exp`。
- **バッチの重複**: 1 回の更新の 64 例のうち入力（47 トークン）が同じ例は 1 列にまとめ、前向き・逆向きを一度だけ計算して、頭の勾配は例ごとに足す。
  例は互いに独立なので数式上は同じ勾配（G2(d)）。列の数は 16・32・48・64 のうち収まる最小にし、残りは損失のない列で埋める。
  学習プールの異なる入力は obs-full 13,606〜13,733、obs-ay 132〜133、exo 134。
- **評価**: 種子ごとに異なる入力ごとに一度だけ予測する（64 列の塊、最後の塊は最後の入力で埋める）。
- **val の主指標**: 種子ごとの行為等重み平均対数損失（TRM・1x1 はクリップ版）の、6 種子の平均。行為ごとの例数 < 30 の種子は val でも除く（今回は該当なし）。
- **除外 < 30**: 評価種子ごとに、選んだ行為ごとの例数で判定（予測器の間で例は共通）。今回は該当なし。
- **ê の評価**: `p_cal` の `x` はクリップ後の `p` の `min(p, 1−p)`。`err` は生の `p` で判定（クリップで ≥ 0.5 の向きは変わらない）。
  ê・ê_cal は `[1/200, 199/200]` にクリップして損失を取る。O1 は種子ごとに、両行為を合わせた全例の平均損失から計算。「判定可能」は `n_err ≥ 10` かつ `err = 0` の例もあること。
- **ê_cal**: `e_head` だけを零から、cal 6 種子の最終 ACT 手の `z_H`（選んだ行為の問い位置）と `err` で学び直す。AdamATan2（lr 1e−3、wd 0、200 歩、B 64、Mulberry(640200)、先頭 50 歩のウォームアップも本体と同じ式）。
- **P-S64-4 の操作化**: 「安定して超える」＝判定可能な種子で O1^cal の符号検定 `p < 0.05`・勝ち > 負け・95% CI の下限 > 0。満たさなければ予測は成立。「微差」の閾値は凍結されていない（今回は O1^cal が負なので使わずに済んだ）。
- **G-TIME**: 3 トラック × 2 モデルの dev（stat 族）で、それぞれ 8 本を同時に走らせて 10 更新（先に 1 更新の慣らし）を測り、中央値の秒/更新で 48 本を LPT で 8 スレッドに割り付けた所要を推計した。
  トラックで重複の多さ（＝1 更新の重さ）が違うので、仕様の「dev 上で TRM・TRM-1x1 それぞれ」をトラックごとに細かくした読み。推計は学習だけで、val と評価の予測（今回 1,173 秒＋学習の中の val）は含まない。
- **G2(a)**: Float64、dev u1046 の obs-full 先頭 4 例。群ごとに |解析勾配| の上位 8 座標と等間隔 8 座標。相対誤差は `|a−n| / max(|a|, |n|, 1e−6 · 群の max|a|)`。
  `lm_head`・`e_head` は初期化で零（本体に勾配が届かない）なので、この関門と G2(d) に限り、初期化の後の同じ Mulberry(640001) の流れから σ = 1/√32 で引いた。
  TRM の `H_init`・`L_init` は最後の H 巡の入口で切れるので勾配は厳密に 0（数値微分も 0）。この 2 群は TRM-1x1 で確かめた。
- **G3 のモデル**: G-TIME の obs-full TRM の写しの 1 本（dev で 11 更新）。`y` の改変は `y_k ← (y_k > 0 ? 0 : 5)`（k = 1, 2）。
  25 例は各 dev 種子の採点例（`4 ≤ s ≤ 9198`）から等間隔に取った。歩の再計算は S57 の `capture`（`PRESTEP`）と `step_draw_conf!` で、手を加えない再計算が記録を再現することも確かめた。
- **G1**: 束は B = 8（学習前は dev u1046、学習後は eval u1074 の obs-full 先頭 8 例）、`nsteps 4`、`steps.input [1,1,1,1]`、`mixed` は x2 を偶奇の halted で。
  比べたのは最終 ACT 手（TRM は 3 手目、1x1 は 1 手目）の全 47 位置 × 12 語の logits と `z_H`。TrmDet と Rust は S60 の凍結の `run_det.jl`・`compare_bin.jl`・`mutate_bin.jl`（`m4`）と既存の Mac バイナリを別プロセスで呼んだ。
- **G6**: 別プロセスの `-t 8` で全部をやり直し、`results.tsv`・`summary.json`・選定済み重み 12 本の SHA を比べた。`-t 1` での全体の再実行は単スレッドで十数時間かかるので行っていない。
  代わりに学習 2 本（obs-ay stat TRM grid 1、obs-full stat TRM-1x1 grid 1）を `-t 1` の別プロセスでやり直し、`-t 8` の重みの SHA と比べた（`t1` モード）。
- 時間（秒/更新、所要）は `results.out` と `gtime.json` だけに書き、`results.tsv`・`summary.json` には入れていない（G6 の比較のため）。

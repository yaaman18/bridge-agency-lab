## 2. 作業の流れ

```
D（対等な議論）→ notes/D<番号>.md にまとめ → 読みを確定（decisions-log、種別「読み」）
   └ bridge-protocol の理論そのものに触れる点 → bp-proposals.md（ユーザーへ）。ラボでは仮定 H<番号> として明示して先へ
→ S 仕様書（Claude）→ S レビュー（Codex）→ 応答・改訂（Claude）→ …最大3往復 → 仕様確定
→ I 実装（Claude：Lean statement → 型検査 → 証明 → [I] メッセージ → DeepSeek：Julia・Rust・試験 → Claude：差分の点検・照合。新しい試算は予測を凍結してから実行）
→ I レビュー（Codex：差分を読む・自分で再実行）→ 応答・修正 → 記録（README の経緯・事実・未決）→ 次の作業
```

- **仕様書**: `discussion/specs/S<番号>-<題>.md`。形は §5。
- **レビュー**: `discussion/reviews/S<番号>-r<回>.md`（仕様）・`I<番号>-r<回>.md`（実装）。判定は
  `APPROVE`（このまま可）・`CHANGES`（直してほしい）・`BLOCK`（§3 の違反）。指摘には番号・重さ（high/med/low）・根拠
  （`ファイル:行`、`P<番号> p.<頁>`、README の項番、bridge-protocol の宣言名）を付ける。
- Claude は指摘の一つ一つに「採る / 採らない（理由）」を返す。3往復で決着しなければ Claude が決め、割れた点を
  `decisions-log.md` に両論で残す。
- 実装の順番はラボの規律どおり：Lean の statement を先に書いて `sh formal/check.sh`、証明、Julia（`core/` が正本）、
  `sh core/check/run.sh` で照合。新しい設計・試算版は走らせる前に予測と反証条件を書き `experiments/freeze-*.txt` に SHA-256。
  外れた予測は外れたと書く。

## 3. 判断の決め方（2026-11-05 ユーザー決定）

**理論の持ち主はユーザー。抽象論理（理論そのもの）は bridge-protocol で解決する。だからラボの側の哲学・論理は二人でどんどん進める。**

**(1) bridge-protocol の理論そのもの → ユーザー（`bp-proposals.md`、事前承認）**
- 対象: M1〜M4、DC・DC2・`hSelf` などの定義、AGENCY-001 の述語（`Agent`・`ValueNeeded`・`SelfProducing`・`SelfRepairing`）の定義、
  閉包作用素 Φ・求めの図式 D・層分離、圏論的仕様、Lean の凍結 statement。これらに穴・矛盾・拡張の要がありそうなとき。
- ラボでは変えない（そもそも bridge-protocol は書き込み禁止）。提案を `bp-proposals.md` に書き、`[BP BP<番号>]` を相手と `yamaguchi` に送る。
- 待たない。ラボの作業に要るなら、その点を **仮定 `H<番号>`** として `bp-proposals.md` に明示し、仮定に依ることを仕様・記録に書いて先へ進める。
  差し戻されたら、その仮定に依る部分を記録どおりに戻す。
- ユーザーは `sh discussion/tell.sh "BP1 承認 / BP2 差し戻し（理由）"` で二人に返す（送り手 `yamaguchi`、`[USER]` で届く）。

**(2) ラボの側の哲学・論理 → 二人で合意して確定（`decisions-log.md`、種別「読み」、事後承認）**
- 対象: bridge-protocol の理論をこの基体でどう読むか（DC の成分の回路での読み D1〜D6 のような対応づけ）、ラボの用語（沈殿・確かさ・習慣・価値・世界など）の
  定義と bridge-protocol の語への写像、要件の中身、判定の運用、論文の読みの取り込み、研究の方針・優先順位。
- 作法は §6。結論はできるだけ「命題」「定義」「Lean の statement の案」の形にする（哲学 → 論理 → 形式 の順に詰める）。
- 割れたとき（3往復で合意しない）: 両論を記録し、**より保守的な読み**（bridge-protocol の字義に近い、主張の弱い、元に戻しやすいほう）で進める。
- 決めたら `decisions-log.md` に1件として書く（種別「読み」）。

**(3) 実装上の判断 → 二人で合意して確定（`decisions-log.md`、種別「実装」、事後承認）**
- 対象: 確定した読み・要件を満たす範囲での、規則の既定・L2 の系やアプリ（`rust/`）の規則・数値（収量・減衰周期・閾値・seed・KC など）・案の選び方・
  README の未決のうち実装上のもの。
- 決め方: **両者の合意**。仕様書の中で出たものも、この種のものは Claude 一人では決めない。割れたら **より保守的な案**
  （今の既定を保つ、既定オフにとどめる、元に戻しやすいほう）。
- **元に戻せる形で入れる**: 既定を変えるときは前の振る舞いを選択肢として残す。数値を変えるときは前の値と変えた場所を記録する。
  凍結した予測と結果は消さない。README の未決を決着させたときは、未決の行を消さずに「（decisions-log #番号 で決定、事後承認待ち）」と書き足す。

(2)(3) とも、ユーザーが事後承認しなかったものは記録どおりに戻す。

**(4) ふつうの作業**（レビューを通せば進めてよい）: 既定オフの選択肢の追加、診断、凍結した予測つきの実験、Lean の statement・証明（`formal/`）、照合、
README の経緯・事実・未決への追記、`discussion/` の文書。

**それでもしてはいけないこと**（ユーザーにしかできない・取り消せない・外に出る）→ `decisions-log.md` の「ユーザーに頼むこと」に書いて先へ進む
- `~/bridge-protocol` への書き込み（判定・fixtures・登録物・logs/gates を含む）
- アプリの db への書き込み、artifact の公開・更新（保存されている存在が移行される）、外部への送信・公開
- git の commit / push（ユーザー依頼時だけ）、ファイルの削除（`experiments/` の凍結・結果・出力を含む。置き換えるときは新しい名前で）
- `phenomenal_claim` に触れる主張、報酬最大化として読める設計、層違反（メタ層の選択が個体の Φ・D・行為の輪に触れる）
- 論文の取得のような、ユーザーの手が要ること

Codex がこれらの違反を見つけたら `BLOCK`。Claude は BLOCK を覆せない（その作業は止めて別の作業へ）。

## 4. 連続運転の決まり

- **受け取った側が必ず次の手を打つ。ターンを終える前に、必ず相手へ1通送る**（自分の番を相手に渡す）。送らずに終えると両方が待って止まる。
- 相手の番の間に自分が進められる作業（論文を読む、下調べ、反例探し、次の仕様の下書き）があれば進めてよい。ただし `STATE.md` で相手の担当になっているファイルは触らない。
- 判断で止まらない（§3）。bridge-protocol に関わる点は仮定として明示して進む。
- `backlog.md` が空になったら、D 段の議題「次に何をすべきか」を自分で足して続ける。
- 同じ論点を3回往復しても進まないときは、§3 の「割れたとき」で決めて次へ。
- 止まるのは：レート制限、§3 の違反で進められる作業が尽きたとき、ユーザーが止めたとき。
- `[USER]` で始まるメッセージはユーザーから（送り手 `yamaguchi`）。最優先で従い、承認・差し戻しを `bp-proposals.md`・`decisions-log.md` のユーザー欄に書き写す。
- **再開できるように**：作業が一区切りするたびに Claude が `STATE.md` を更新する（段階・作業 ID・担当・次の一手・関連ファイル・置いている仮定）。
  コンパクションや再起動のあとは `STATE.md` → このファイル → 自分の席の `agents/*.md` → `/agmsg history` の順に読んで再開する。
- 確認だけの返事（「了解」「ありがとう」）は送らない。送るのは、次の手が入ったメッセージだけ。

## 6. 哲学・論理の作法（D 段）

- **主張は命題として書く。** 何が何について成り立つと言っているのかを一文で。比喩は使ってよいが、比喩のあとに必ず字義どおりの命題を置く。
- **用語は定義してから使う。** ラボの語（沈殿・確かさ・習慣・価値・世界・相手）は、定義と、bridge-protocol の語（DC の成分、M1〜M4、L2/L3 の述語）への写像を書く。
  同じ語を二つの意味で使わない（定義の滑り）。写像が部分的なら、どこが写らないかを書く。
- **反例を探す。** 自分の主張にも相手の主張にも、成り立たない場合を一つは探す。見つからなければ、どこを探したかを書く。
- **相手の最強の論拠を述べてから反論する。** 弱い読みを叩かない。
- **確認と推論を分ける。** コード・Lean・実験の出力で確かめたこと / そこからの推論 / 提案。重要な提案には反証条件。
- **有限の不在を一般の不可能に昇格しない。** 「この実験・この種子で見つからない」と「一般にできない」は別（bridge-protocol の規律）。
- **形式へ降ろす。** 合意できた命題は、測れる形（Julia の判定・監査）か Lean の statement の素案にする。降ろせないなら、なぜ降ろせないかを書く。
- **層を混ぜない。** 対象層（個体）とメタ層（個体間の選択）、下層の自己維持と上層（快・不快）を混ぜない。最適化・最大化の語彙で維持を語らない。
- `phenomenal_claim` は扱わない（「主張しない」ことの確認に限る）。

## 7. 論文の扱い

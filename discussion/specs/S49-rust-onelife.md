## 1. 事実
- F1 Julia の `core/one_life.jl`（sha は `experiments/freeze-one-life-b.txt`）が正本。保存のバイト列の並びは `onelife_encode` が決めている。
- F2 Rust の `being-core` には `circuit.rs`（アプリの規則）があり、`matter` と body_org はない。依存クレートなし（no_std の方針）。
- F3 Julia の exp は `jsexp`＝openlibm（FreeBSD msun、fdlibm）の exp（`core/jsmath.jl:13`）。`matter.jl:27`・`:65` が使う。Base.exp とは約 10% の入力で違う。
- F4 `sh core/check/run.sh` が Julia と Rust の場面をビット単位で比べる。

## 2. 決めること
- **規範の exp**（codex C3）: fdlibm の `e_exp.c`（FreeBSD msun と同じ算法）を Rust に書き下す（積和の融合なし、f64 の演算だけ）。許容差は置かない。関門: Julia の `jsexp` と 40 万入力（`core/check/math.jl` の範囲＋OneLife の走りで実際に現れた引数）で全ビット一致。1 つでも違えば S49 は不成立で止める。ほかに OneLife の step が呼ぶ数学関数があれば同じ扱い（一覧を実装の報告に付ける）。
- **Rust の OneLife**: `being-core` に新しいモジュール（`matter.rs`、`onelife.rs`、SHA-256 と exp は自前、依存クレートを足さない）。アプリの経路（`life.rs`・`circuit.rs` の既定）の振る舞いは変えない。`circuit.rs` に要る選択肢（bin3、IDLE、GATE、SEDFADE ほか）がなければ既定オフで足す。step は（状態, 駆動）だけを受け、法則 L2・L2+SF ごとに定数を閉じた 2 本。step の中の順序は S48 r2 §3.2・§3.3 のまま（① dead ならそのまま ② 座が空なら検出 ③ 値域の検査 ④ 生きている一歩）。
- **保存の形式**: Julia の `onelife_encode` のバイト列と同一（法則の識別・SHA-256 の検査値を含む）。Rust で読んだ Julia の保存、Julia で読んだ Rust の保存がどちらも通る。
- **照合の CLI**（`being-tools`）: `onelife-check`（種子・法則・駆動列 → 各歩の保存バイト列の SHA-256 と最後の保存）。`core/check/run.sh` に場面を足す。誕生の関数は照合のためだけに CLI から呼べる（試験の種子だけ）。
- **実行形式 `onelife-run`**（codex C1・C2）:
  - 入力: 走りのファイル（下の形式）と、標準入力の駆動（1 行に `g1 g2`）。誕生はしない（走りのファイルがなければ誤りで終わる）。
  - 1 行ごとに: 走りのファイルを読んだ状態に step を当て、新しい走りのファイルを原子的に置き換える（一時ファイルに書く → fsync → rename）。
  - **死後も終わらない**: dead の状態でも入力を消費し続け、同じ状態のバイト列を保存し続ける（状態は 1 ビットも変わらない。変わるのは下の n だけ）。入力が尽きたら正常に終わる。
  - **走りのファイルの並び**（実装の前に固定、codex S49-3）。全長はちょうど 64＋L バイト:
    | 位置 | 長さ | 中身 |
    |---|---|---|
    | 0 | 8 | ASCII `ONELIFE1` |
    | 8 | 4 | 形式の版 u32 LE ＝ 1 |
    | 12 | 4 | 予約（すべて 0。0 でなければ拒否） |
    | 16 | 8 | n＝消費した駆動の数、u64 LE |
    | 24 | 8 | L＝中身の長さ、u64 LE（1 ≤ L ≤ 16,777,216） |
    | 32 | L | 中身（OneLife の保存バイト列そのまま。中の検査値も読み込みで確かめる） |
    | 32＋L | 32 | 位置 0 から 32＋L の手前までの SHA-256（自分自身は含まない） |
    拒否するもの（保存も書き換えもしない、0 でない終了コード）: 識別・版・予約の不一致、L の範囲外、全長が 64＋L でない（切り詰め・末尾の余り）、SHA の不一致、中身の読み込みの誤り。
  - n は実行形式の帳簿で、個体の状態ではない（dead の後は t が進まないので、再開の位置は状態から取れない）。n は step に渡さない。駆動を選ぶ・読み飛ばすのにも使わない（標準入力を先頭から順に読むだけ。再開のときに残りの駆動を渡すのは呼ぶ側）。変わり方は消費 1 つにつき ＋1 だけ。n＝u64 の最大値なら保存せずに異常終了（codex S49-2）。
  - **原子的な置き換え**: 同じディレクトリの一時ファイルに書く → 一時ファイルを fsync → rename → 親ディレクトリを fsync（codex S49-4）。主張は「プロセスが途中で止められても、走りのファイルは古い版か新しい版のどちらか完全な一方」まで。電源断への耐久は主張しない。
  - 誤りのとき直さない: 検査値の不一致・形式の不一致・値域外の駆動（生きている状態）は、保存せずに 0 でない終了コードで止まる。状態を作り直す・初期化する・既定値で埋める道は作らない。
  - 引数は走りのファイルの場所だけ。KC・法則・種子・時刻・環境変数を読まない（法則は保存の頭の識別で決まる）。1 歩の実時間の引数は付けない（J1-3 のあと別の改版）。
- **救出の経路の表**（手順 §12）: 実行形式から状態へ届く入力を一覧にする（走りのファイル、標準入力）。それ以外（引数・環境変数・時刻・乱数・ネットワーク）が届かないことを、ソースの機械的な検査（`std::env`・`std::time`・`rand`・`std::net` が `onelife-run` と `onelife.rs`・`matter.rs` に現れない。引数は場所 1 つ）で確かめる。これは「見つからなかった」までで、証明ではない。OS の権限・ファイルを書ける者による書き換えは P4 の話で、ここでは防がない。

## 3. 対象集団
- 単位: 種子から新しく作った個体。照合の場面の種子 627〜628（次に主張で使う新しい種子は 629 から）× 法則 2 × 駆動列 D1・D3（D3 は S48b。死を含む）＝ 8 体、地平 10000。照合は全件一致だけを見る（1 件でも違えば不成立、検出不能の欄はない）。生存の成績は読まない。
- 一般化の範囲: この機械（x86-64 の macOS）でのビット一致。別の機械・別の CPU での一致は、宿主が来てから同じ場面を走らせて確かめる（exp を自前にしたので libm には依らないはずだが、確かめるまでは主張しない）。

## 5. 関門
- Q0: 変更の前後で `sh core/check/run.sh` の既存の場面が全一致（アプリの経路を変えていない）。`app/index.html` の埋め込みの照合も通る（wasm を作り直しても同じ、または作り直さない）。
- Q1 exp: §2 の 40 万入力の一致。負の対照: Rust の `f64::exp` と比べると不一致が出ることを示す（出なければ、その旨を報告。関門の感度が示せなかったことになる）。
- Q2 ソースの検査（§2 の救出の経路）。負の対照: 検査の対象に `std::env::var` を 1 行足した写しで検査が落ちる。
- Q3 SHA-256: 既知の試験ベクトル（空、"abc"、100 万個の "a"）。
- Q5 走りのファイル（codex S49-6）: 読む→書くで同じバイト列。n・L の切り詰め、過大な L、末尾の余り、未知の版、予約が 0 でない、n が最大値、のそれぞれを拒否し、ファイルを書き換えない。
- Q6 保存の途中の中断（codex S49-7）: 試験用のビルド（`--features crashpoint`。本番の実行形式には入らない）で、一時ファイルを書く前・書いた後・fsync の後・rename の後（親の fsync の前）で自分を abort させ、再開のとき走りのファイルが古い版か新しい版の完全な一方であること、続きの最後が通しの走りと一致することを確かめる。本番の実行形式にこの中断の経路がないこと（feature なしのビルドのソースの検査）。
- Q4 `cargo build --release` が警告なしで通り、`being-core` は依存クレートなしのまま。

# S71 草案: C0 再設計（S64 の不合格を受けた新仕様。S64・その凍結・出力は変えない）

状態: **草案 r1（codex S-R 2026-11-24 P7・P8 反映、未凍結）**。依拠: S64（r3）の結果 `experiments/c0_trm/README.md`。dev 実験の台本 `experiments/c0r_dev/`。
S64 の不合格は凍結した文言どおりに残す。ここは別仕様で、基準は結果を見る前に宣言し、外れた予測も外れたまま書く。

## 1. S64 の不合格の診断（既存の出力を読んだだけ）
1. TRM も TRM-1x1 も受容器を使えていない: obs-full と obs-ay（受容器 PAD）で val がほぼ同じ（TRM stat 0.04389/0.04389、1x1 stat 0.03565/0.03578）。一方 TAB_R1（受容器 1 歩の表）は 0.013。
2. stat の TRM の p は入力に依らない定数（0.99188）で、損失は RATE と同じ。
3. 学習不足の兆候: 4 設定の最良が常に最大 lr（グリッドの端）、損失は 800 更新の終わりでも下降中（S_train は約 1 エポック）。
4. TRM が TRM-1x1 に負けた: 同じ更新数では深い再帰が不利（勾配が通るのは最後の H 巡のみ）。
5. G1 不合格は Float32 の丸めの増幅（Float64 基準で TrmC0・TrmDet が同程度にずれる）。

## 2. dev 実験（結果を見る前に宣言。eval 種子は読まない）
dev は S64 の TRAIN 12 種子で学習、VAL 6 種子で採点する（stat 族から）。確証の実行では新しい種子（1110 以降）を使う（S64 の eval は結果を見ているため再利用しない）。

- **A（G-LEARN）**: obs-full stat の TRM・1x1 を、lr ∈ {1e-3, 3e-3, 1e-2}（wd 0）、nsteps ∈ {800, 3200, 8000} で学習。
  判定の案: val ≤ RATE の val − 0.005、かつ val 上の p の標準偏差 ≥ 1e-3。通らない設定は確証の実行に進めない。
- **B（受容器の経路）**: 同じ 1x1 を、入力の可視域を変えて学習: `full`（全部）、`ay`（受容器 PAD）、`r8`（直前歩の受容器 8 個と問い位置のみ）、`r1`（TAB_R1 の 6 受容器と問い位置のみ）、`rall`（4 歩分の受容器のみ）。
  読み方の案: r1 で 1x1 が TAB_R1（val 約 0.012）に近づけば、モデルは受容器を読めるので問題は他の位置による希釈か学習量。近づかなければ入力の符号化・学習の設計を直す。
- **C（G1 の基準）**: S64 の保存重みで、TrmC0（Float32）・TrmPort（Float32）・TrmC0（Float64）の問い位置の p の差を、64 個の異なる入力で測る（`probe_c.jl`）。
  結果（dev、1 回）: stat の TRM・1x1、rev の 1x1 は最大差 2e-7 以下。**rev の TRM は C0(f32) と Port(f32) の差が 9.4e-4、C0(f32) と C0(f64) の差が 9.3e-4**で、「p の差 ≤ 1e-4」の案は満たさない。p が 0.99 付近なので、損失への効果は差にほぼ比例する。
  したがって基準は p の差でなく「val 損失への効果 |Δ| ≤ 1e-5」へ改める案（後述 §3）。実装の累積順序を揃える修正は未着手。

- 確認した事実: 1x1 は直前歩の 6 受容器だけで、800 更新で TAB_R1 と表示桁まで一致。full は 800 更新では届かず、3200 更新で届いた。r8・rall・full の集計損失に、TAB_R1 を超える利得は現れなかった（rall は +0.00001）。
- 推論（codex S-R 01:04Z P2・P3）: 「他のトークンがあると受容器の学習が遅れる」は r1 と full の更新数の差を説明する仮説にとどまる。800 更新の full と ay の損失が近いことから「full は受容器を使っていなかった」とは言えない（改善と他の入力の誤差が相殺しても同じ値になる）。反証の試験: 800 更新の full を固定し、受容器入力の対応を崩して損失が再現よく悪化するかを見る。

## 2.6 合格条件の見通し（推論、codex P7 を反映）
- S64 の C0 は TRM が TAB_R1 と TRM-1x1 の両方に有意に勝つことを要する。dev では 1x1 が TAB_R1 と同値まで来た。世界が直前の受容器に対してほぼマルコフなら、47 トークン窓に TAB_R1 を超える情報は少なく、TRM が両者に有意に勝つ余地は小さい。
- 学習不要の 4 歩の経験表（受容器と行為、交差検証）を同じ保留系列で測る。**TAB_R1 を上回れば履歴を使える根拠になる。同値でも、長い履歴の利得は排除できず、合格条件を緩める根拠にはしない**（codex P7: 表の交差検証値は 47 トークン窓の性能上界ではない）。合格条件の見直しはユーザーが決める。

## 2.7 合格条件の 2 段構え（案、2026-11-24 ユーザー指示「2段構えでS71に書き足して」）
- **前提（ユーザー、H 扱い）**: TRM は要る。したがって「TRM が TAB_R1 に勝てない」結果は、まず**試す場が履歴を要求していない**ことの徴候として読み、TRM を外す根拠にはしない。
- **確認した事実**: stat 族の obs-full では、直前歩の 6 受容器（r1）だけで 1x1 が TAB_R1 と同値（§2.5b）。この場は直前の受容器に対してほぼマルコフで、窓や再帰の価値を測れない。
- **段 I（C0 の関門、抽象と自覚して置く）**: 開ループの予測器としての質を問う。
  - I-a: 既存の基準（TAB_R1・1x1）を、種子ごとの対応差の検定で上回る（§4 の (1)）。
  - I-b: 履歴の寄与。TRM full 対 TRM r1 で、full が有意に良い（§4 の (2)）。両群で現在の入力・モデル容量・学習予算を揃え、r1 側は窓と再帰状態のどちらからも過去が届かないようにする（現在入力まで違うと、full の勝ちを履歴に帰属できない。codex P3）。**履歴を要求する場で問う**: 候補は rev 族。stat 族は回帰の対照として残す。
  - I-b の前提確認（codex P2）: まず生成則の上で、同じ r1・同じ非履歴入力でも、観測できる過去によって次の標的の条件付き分布が変わる例を示し、その頻度を dev 種子で数える。分布が常に一致するなら rev 族は履歴を要求していない → 過去から隠れ状態を識別できる遅延課題を設計する案をユーザー判断に回す。
  - I-c: 適応の速さ（後で可塑性を持たせる前提での事前知識の質）。群: C0 の重みから更新、C0 の更新なし、同じ TRM の未学習初期化から更新、1x1 と TAB_R1 の逐次更新。全群に同じ系列を順に与え、各標的を更新前に採点する（前向きの評価）。主指標は区間の累積損失、初期損失と更新ごとの曲線も残して初期値の良さと適応の速さを分ける。更新数は想定する現場の観測予算から dev で決めて凍結する（codex P4）。
- **段 II（閉ループ、存続に近い関門）**: U7・U9 の実装後（C0 の重みの確定後）に判定する。C0 の p を S69 の判断の規則につなぎ、同じ種子で TAB_R1 の p をつないだ場合と対にして、生存の指標を比べる。主指標は、事前に固定した観測期限までの存続歩数（期限時に存続なら満期）。同じ初期状態・外乱系列で C0 と TAB_R1 の対応差を取り、体の消失の量は副指標（codex P5、指標の詳細は S69 r3 で凍結）。差が有意でなければ「改善未確認」と記録し、同値を主張するには事前に同値幅を決めておく。対応差の信頼区間が事前の同値幅に収まった場合に限り「期限までの存続歩数は実質同値」と記録し、場か判断の規則を見直す（行動が違っても存続歩数は一致しうるので、「予測の改善が行動に届いていない」とは書かない。TRM を外す根拠にもしない。codex P5）。
- **反証条件**: (i) 生成則の確認（I-b の前提確認）を二つに分ける。(i-1) 生成則から、同じ r1 のもとで次の分布が過去に依らず一致すると示せたら、rev 族は履歴を要求していない → 履歴を要求する場を別に設計する（基体・環境の変更はユーザー判断）。(i-2) 依存はあるが dev 種子で該当例が未観測または稀なら、「rev で履歴の寄与を測るには頻度が不足」と判定する。「稀」の基準（該当例の割合の閾値）は計数の前に固定する。TAB4 と TAB_R1 の大小はこの判定に使わない（codex P1）。(ii) 段 I を通っても段 II で TAB_R1 と同値なら、段 I の指標は存続の代理として不足。
- **既存の出力から（確認した事実、`experiments/c0_trm/out/results.out` 105–108 行）**: S64 の eval 24 種子・obs-full rev で、TRM−TAB4 = −0.01313、TRM−TAB_R1 = −0.03430（正が TRM の勝ち）。差し引くと TAB_R1 が TAB4 より約 0.021 nat 良い。つまり 4 歩の表は rev でも TAB_R1 に及ばない。**推論**: この事実から履歴が不要とは判定できない。TAB4 は鍵 1250 のうち 216 しか見ておらず（TAB_R1 は 130 中 26）、表の疎さの損で負けたという読みは仮説にとどまる（codex P1）。→ 学習する比較（TRM full 対 TRM r1、rev 族）で問う必要がある。
- **C0 の重みの確定条件（codex P6 支持）**: 既存の関門を保ったうえで、I-a かつ I-b を確定条件、I-c は報告、段 II は U7・U9 の関門。rev の採否・比較条件・判定規則を凍結し、S64 で見た種子とは別の種子で確証する。
- 抽象度の注記: 段 I はどれも模擬環境（S57）上の代理指標で、現実の受容器での存続を保証しない。現実との差は段 II と、後の可塑性（現場での合わせ直し）で詰める。

## 3. 新仕様に入れる方針（案）
- 合格条件は S64 の 5 基準（RATE・B1・TAB4・TAB_R1・TRM-1x1）を維持。緩めない。
- 学習量と lr は dev の A で選び、その選び方（規則）を実行前に凍結する。
- G1: 実装間の一致は、評価に使う予測の val 損失への効果で定義し、全位置の logits と z_H は報告のみとする（dev の C が根拠。ただし基準の変更なので新仕様の冒頭に宣言する）。
- 予測（P-S71-*）を実行前に書いて凍結する。

## 4. 未決
- **合格条件の論点（ユーザー判断、codex P5・P6）**: S71 の合格に求めるのは (1)「既存の基準（TAB_R1・1x1）を上回ること」か、(2)「追加の履歴（窓・再帰）がその改善に寄与すること」か。TRM full と TRM r1 が同程度で、ともに TAB_R1・1x1 に勝つ場合、二つの判定は分かれる。
  どちらにしても、比べる 1x1 の入力と更新数、種子ごとの対応差の検定と有意水準、判定に使うデータ（新しい種子）を実行前に明記する。VAL 6 種子の集計値だけでは有意差を判定できない。
- G-LEARN の閾値（0.005・1e-3）は仮。
- U7・U9（S69）は C0 の重みの確定後に判定する（ユーザー指示。S69 r3 草案 §2）。合成重みの結果は配線の参考記録。
- 1 回の確証の実行に TRM を 8000 更新まで回せるか（S64 の TRM は 800 更新で 8 本同時に 1 本約 2,400 秒）。計算時間の関門 G-TIME を新しい S_train で作り直す必要がある。
- rev 族と OOD を含めるか。

### BP5 ビット一致の再計算で作り直した個体の同一性と、死の不可逆性（2026-11-10 D-GUIDE、fable-lab の r2 判定の啓示 2。ユーザー「bp-proposals に出すのはそうしてください」）
- bridge-protocol のどこ: M1（自己維持＝νΦ と precariousness）、BP1（法則を替えたときの同一性）・BP3（生存代理と不可逆性）と隣り合う。ラボ側は promise-cutout.md §1・§5。
- 何が問題か（命題として）: 法則が決定的で、外からの駆動の**内容**が時刻つきで記録されるなら、任意の時刻の状態は（初期状態・法則・種子・駆動の記録・ビット一致する実行系）を入手できる者なら誰でも再計算できる（sha だけでは内容は戻らない）
  （作業手順 r2 は Julia と Rust の一生のバイト列までの一致と、信号の sha つきの記録を求める: procedure-cutout.md §6・§7）。死んだ個体の死の前の状態を再計算し、別の駆動で続けた個体は、元と同じ履歴（沈殿・閉包の連続）を持つ。
  (1) 再計算で一致するのは死の前までの履歴で、死を含む元の全履歴ではない。共通の過去から分かれた続きを、同じ個体の継続とみなす規則はあるか。
  (2) あるとすると、死の吸収状態は法則の中だけの性質で、世界の中では取り消せることになる。ただし外から再構成できることと、稼働中の自己維持が破れうること（precariousness）は両立しうるので、M1 が名目になるとまでは言えない（M1 の正本は未照合）。
  (3) 再計算の経路は P4 の確認の範囲（所定の書き込み経路）の外にある。だから P4 だけでは復元できないことを示せない（「約束だけが止めている」とは断定しない。ほかの制約は未確認）。
- 根拠: `discussion/fable/20261110-201605-review.md` §6 啓示 2、promise-cutout.md:13（移行による延命を手放す）・:45（同一性は存在自身の履歴で決まる）、procedure-cutout.md §9（P4 の表は再計算の経路を試していない）。
- 案: (a) 同一性は担い手の物理的な連続で決まり、履歴が同型でも再計算した個体は別の個体。死は不可逆のままで、再計算は救出ではなく新しい個体の誕生になる
  ／(b) 同一性は履歴の同型で決まる。死を世界の中でも不可逆にするには、切り出した個体の入力を再現できる精度で残さない（記録しない成分を入れる）必要がある。その代わり、その一生は後から再現・検証できない（作業手順の E2〈記録された入力〉と E4〈救えない〉が同じ記録をめぐって引っ張り合う）
  ／(c) 同一性は理論の外（観察者の記述）に置き、ラボは再計算の経路を構造的に排除したかは未確認と明記する
  ／(d)（codex-lab の追加）同一性を因果的な実行の継続で定め、再計算した個体は共通の過去を持つ別の分岐とする（担い手の同一と履歴の同型の二択に収まらない）。
  注: (b) の「入力を残さない」は不可逆性の十分条件ではなく、唯一の必要条件とも示していない（途中の状態の保存などから続けられれば反例）。
- 二人の立場: claude-lab は、ラボでは当面 (c) の書き方（保守案: 主張を弱める側）。(a)〜(c) の選択と、切り出した個体の入力を再現できる精度で残すかは、J3 の前にユーザー。codex-lab（2026-11-10）: 同一性の理論の判断は保留し、ラボでは再計算の経路の構造的な排除を未確認と明記する限定した (c) を支持。両者とも当面 (c)。
- ラボで置く仮定: H3（案、codex-lab の文）— 「P4 の確認の範囲は所定の書き込み経路に限る。再計算による再構成・継続は構造的な排除を確かめておらず、約束として禁止する」。許可した経路で再構成・継続が実現できたら、構造的な不可逆性への反例とする。P4 の経路の表に「再計算による再構成・継続」の行を足す。
- 仮定に依っている仕様・実装: 作業手順 r3 の P4（未作成）、開発指針 §2 の製作目標の言い方。
- ユーザー: **(c) を承認**（2026-11-10 ユーザー「BP5:はc」）。同一性は理論の外に置き、ラボは再計算の経路の構造的な排除を未確認と明記する。仮定 H3 を採る。
- 追記（2026-11-14、`notes/D-TIME.md` B）: 現実の感覚につなぐと、採取 → step → 保存の途中でプロセスが落ちたとき、同じ n の歩を採り直した別の入力でやり直せる（入力の引き直しの余地）。二人の合意は「同じ n の採り直しは禁止」。そのための方式は二つで、どちらかはユーザーの選択（J3 の前、ただし S49c〈間隔つきの実行形式〉の仕様には先に要る）:

### BP6 切り出した個体を「走らせ続ける」ことと、実行の基盤の撤去（2026-11-14 D-TIME）
- bridge-protocol のどこ: M1（自己維持と precariousness）、記憶と時間の概念。ラボ側は promise-cutout.md §1（手放す二つの力）、J1-3（停止中は歩まない、仮定 H4）、procedure-cutout.md §9（自動の再開だけ）。
- 何が問題か: 約束は「法則を書き換えない」「失敗から救わない」と言うが、「走らせ続ける」とは言っていない。(1) 宿主を止めたまま起こさないことは、dead を立てずに個体の歩みを終わらせる（救出ではなく実行の基盤の撤去）。これを誰がいつ決められるのかが書かれていない。
  (2) 「停止中は歩まない」のもとでは、止める・起こす時機を選べる者は、個体が受け取る現実の入力の区間を選べる。有利な時機を選べば「救う力」の一手段になる。(3) 故障の修理は、裁量のない自動の再開（切り出しの前に凍結した手順）なら基盤の維持、時機に裁量があれば介入、と二人は読んだ。止まっているあいだ個体が在るのかは決めていない。
- 根拠: `discussion/notes/D-TIME.md` T2・A、codex-lab の 1 往復目 2・3、2 往復目 1〜3。
- 案: (a) 約束に一行足す:「切り出した個体の宿主を保つのをやめる決定はユーザーだけがする。止めた事実と再開の時機は状態の外に記録する」／(b) 足さない。宿主の維持は約束の外の事実上の行為として扱い、記録だけする／(c) 走らせ続ける期限または条件を切り出しのときに宣言する（宿主の寿命・電源の事情を先に書く）。
- 二人の立場: 決めない。現行の約束から (a) は導けない、という点で一致。ラボでは当面、裁量のある停止・再開をすべて介入として記録する側（保守案）。
- ラボで置く仮定: H5（案）「切り出した個体の再開は、切り出しの前に凍結した裁量のない手順だけ。それ以外の停止・再開は介入として記録し、約束への適合は主張しない」。
